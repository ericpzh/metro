# Train and passenger model parity

Use this alongside the [model migration checklist](model-migration-checklist.md). The existing Unity review assets establish import, rendering and motion for specific specimens. The production target is the rolling stock and soft-human crowd used by the TypeScript game.

## Train formations and power

The line editor offers **2, 3, 4, 6 and 8 cars** and independently offers **third rail and overhead wire** for all five stock classes. Use `game/src/sim/headway.ts` for the formation menu, `game/src/app/windows/inspector/LineCard.tsx` for the available combinations, and `game/src/sim/stock.ts` for dimensions, doors and stock defaults. The stock-specific `consist` ranges are reference values. The editor's formation menu applies across classes.

Each cell is a production configuration to verify. Mark it with a pass and link the evidence once the Unity runtime assembles it correctly. Keep review fixtures as evidence for the tested specimens.

1. **Start with the actual Zoo train.** Its Line 5 record is **Type L, six cars, third rail**. Replace the two-car Type A proxy when the L formation passes review. Resolve stock, formation, power, livery, model scale and direction from the line and train state.
2. **Assemble from shared car parts.** Generalize the current exporter to accept stock, car role and power-related roof options. Reuse cab and intermediate car assets, gangways, bogies, interiors and door pieces where they share geometry. Use the formation and car index to assemble each consist. Preserve stock-specific door counts, car dimensions and D's cab and end-door geometry.
3. **Port the roof layout explicitly.** Use `TrainPantograph.ts` and `train-pantograph.test.mjs` as the oracle. The overhead layouts specify each powered car and its elbow direction in train-local coordinates. Verify the mounting wells and contact height. Third-rail formations have no pantographs. Confirm travel-direction reversal changes the leading and trailing presentation while preserving the physical mounting positions.
4. **Verify every configuration in code.** Compare overall length, car spacing, door centers and widths, the selected bank's movement and the other bank's closed position, plus pantograph indices and orientation. Render representative short and long consists in Web with both power variants and all five stock classes. Include Zoo's exact configuration and confirm doors line up with the platform.

Use the TypeScript baseline from the repo root:

```powershell
node --test game/test/train-pantograph.test.mjs game/test/train-bogie.test.mjs game/test/train-cab.test.mjs game/test/train-preparation.test.mjs
```

## Passenger source and migration

The TypeScript game renders the **soft-human** crowd. `game/src/render/passengerModel.ts` loads `passenger-approved.json`. `tools/bake-soft-passengers.mjs` builds that atlas and `passenger-activities.json` from the soft-human body, wardrobe, motion and activity generators. The Unity passenger exporter builds a different original humanoid with a separate 15-bone rig. Its review assets are useful stand-ins. Soft-human parity remains open. [Game passenger library](../../game/src/assets/PASSENGERS.md)

1. **Keep soft-human as the source of truth.** Start from `model/src/soft-human/imported-base.js` and the authored wardrobe and activity generators. Use the active bake's source and recipe hashes to identify the exact inputs. Preserve the rig, skin weights, silhouette, proportions, material regions and pose behavior.
2. **Resolve source rights for production delivery.** The repo identifies `HumanBody_Alt.fbx` as the soft-human base and records that its supplied readme contains no redistribution license. Record clearance for the base and its derivatives before publishing that Unity crowd. If a different body is needed for release, treat that as an explicit asset decision and review its fit against the soft-human reference.
3. **Prove one real soft-human variant.** Review `model/scripts/export-soft-human.mjs` for the existing GLB exporter and check what it includes. Use the current soft-human motion and activity bake as the reference for Unity clips or baked pose data. Verify standing and walking on one adult in Unity Web, then compare the same variant and poses against the game.
4. **Expand through the active recipes.** Cover both ages, outfit and material variants, hair, bags and straps, both detail levels, and the active movement and activity sets. Check skin deformation, foot placement and held accessories. Use a shared rendering representation for the crowd and compare selected variants and animation frames in Web before marking the production rows done.
