# Subplan 04 · Unity Web hosting, language and release

Read [the migration index](README.md), the metro web skill, `README.md` under Deploying to Cloudflare, both Wrangler configs, both Worker handlers, `web/src/site.js`, `game/src/app/boot.tsx`, `game/src/app/demoRoute.ts` and `tools/check-demos.mjs`. Start with a local release artifact and a staging Worker. Production requires the owner to approve the cutover and provide deploy access.

## W1. Define artifact and URL contracts

1. Keep `metro-game` as owner of `stationdesigner.com/game` and `stationdesigner.com/game/*`. The wildcard does not cover the bare path, and `/game*` would capture unrelated paths. The root site's `metro` Worker and the stats Worker's routing and builds stay independent. Use `ASSET_PREFIX=/game` and a parser that strips the exact prefix on a segment boundary. It also supports a Worker-host root for previews. [Cloudflare routes](https://developers.cloudflare.com/workers/configuration/routing/routes/)
2. Create a minimal Unity Web template under `unity/Assets/WebGLTemplates/StationDesigner/`. It renders the accessible loading/error shell, checks capability, creates the Unity instance, and passes launch config from an explicit JS/C# bridge before the player opens a save. The shell can set `document.documentElement.lang`, page title, loading text and locale navigation before WASM loads. Expose a fallback link and a readable failure reason. Preserve the desktop-first mobile notice if approved.
3. Package output with a planned `tools/unity-web/pack.mjs`. Input is raw Unity Web output, build provenance, engine-selection config, and the existing TS build for rollback and legacy utilities. Output is a staging directory and a manifest listing release ID, source SHA, entry metadata, every loader/framework/WASM/data/StreamingAssets/template file, content type, compression, size and SHA-256. Generate the manifest from actual build outputs. Fail on absent or duplicate required resources, unrecognized extensions, traversal paths, mismatched digests, stray symbols, cache dirs or unapproved assets. An immutable release ID includes the source SHA and an artifact digest.
4. Keep the existing TS dist at the asset root so the old relative paths, benchmark and lab still resolve. Reserve `/_unity-shell/` for Unity's mutable HTML/config and `/_unity/<release-id>/` for its immutable files. The public URLs for those binaries start with `/game/_unity/` on the apex and `/_unity/` on workers.dev root. Compute the base once from the parsed mount point and the manifest. Build each loader/framework/WASM/data/StreamingAssets URL from that base, including under `/game/en/tanwei`. Never rely on the visible document's directory to resolve Unity files. A deployment uses one explicit release ID for all locale and demo documents.
5. Keep the checked-in Wrangler game config path as the single production owner. While building the port, the normal TS deploy keeps its TS output/config, with a separate local/staging config for the packaged artifact. At promotion, have the game production config point to the packaged asset directory. Set explicit engine mode on the release, for example `GAME_ENGINE=unity`. Setting `GAME_ENGINE=legacy` selects the TS game with the same release packaging. Confirm a diff shows only intended route/asset/binding changes before deploy.

## W2. Implement the path and language contract

Implement the parser as a pure JS function with table tests. Return route kind, mount, locale, canonical path, optional demo ID and engine. Define known paths before checking assets, and preserve query on redirects. The browser carries hash and search across language switches where they apply. Define a stable alias only with owner approval.

| `/en`, `/en/index.html` | Existing 308 to `/en/`. English Play and demo links point to `/game/en/` and `/game/en/{id}`. |

With a trailing slash, first 308 to the slashless demo route. |

1. Implement mount detection for apex, workers.dev, version-preview and local Wrangler. Test both prefixed and root routes on the appropriate hosts. Preserve URL search through 308 redirects with the URL API. Treat reserved binary namespaces as assets before navigation and accept only bounded, validated release IDs and manifest-listed paths. Decode/normalize once and reject ambiguous encoded slashes and dot segments. Keep GET/HEAD behavior consistent.
2. Avoid asset-first short circuits for navigations, redirects and protected payload headers. Initially set `assets.run_worker_first: true` in the Unity release config so route/headers are unambiguous on both apex and root. Serve TS files through the same binding and check all legacy aliases. Measure before narrowing it to path patterns. Keep `not_found_handling: none` and handle shell routing explicitly. Fetch the shell through a known asset location and verify that HTML handling does not send a redirect to an internal pathname. [Static asset and Worker order](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)
3. Inject a small validated config with `mount`, `locale`, `demoId`, `releaseId`, `assetBase` and release mode. Use safe JSON serialization for HTML or a dedicated same-origin endpoint. Use a shared allowlist for the three station IDs generated from the TS list. Never pass URL-supplied arbitrary file paths or HTML into the loader. Wait for C# to acknowledge the selected locale and successfully opened station before dropping the demo path. The English route stays English across reload. Route switching in settings follows [R6](03-runtime.md#r6-complete-ux-and-content-parity).
4. In `web/src/site.js`, retain the existing production `gameHref`, `demoHref`, `benchmarkHref` and `VITE_GAME_URL` contract. If local Unity uses another origin, set `VITE_GAME_URL` for local validation. Update `tools/preview.mjs` only if it becomes the chosen integrated preview for Unity. Prefer exercising the real Worker handler with Wrangler, with the site and stats running separately when appropriate.

## W3. Serve payloads and test response headers

1. First ship a local smoke with raw Unity build files and decompression fallback disabled. Then build Brotli for HTTPS release and keep fallback disabled after edge header tests pass. Use headers derived from manifest type, so `.wasm.br` is `Content-Type: application/wasm` and `Content-Encoding: br`. Set JS to `application/javascript`, data to `application/octet-stream`, and HTML to `text/html; charset=utf-8`. Apply original MIME to the compressed representation and preserve its encoded byte stream. Use Workers `encodeBody: "manual"` when constructing a response around precompressed bytes. Explicitly test that the Static Assets path returns bytes as expected before reconstructing the response. If encoding negotiation or Cloudflare transformation makes it ambiguous, use the tested raw/edge-compression strategy or stream the encoded bytes from R2 with explicit headers. [Unity Web deployment headers](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-deploying.html) · [Workers Response API](https://developers.cloudflare.com/workers/runtime-apis/response/)
2. Use WebGL 2 and single-threaded settings for the first release. Only a separate native/Burst-threading spike introduces cross-origin isolation headers on the Unity game responses and checks required resources, browser capability and integration impact. Confirm loader URLs, font behavior, audio unlock and save bridge in each shipping browser.
3. Set `Cache-Control: no-cache` or stricter for HTML and mutable config, and `public, max-age=31536000, immutable` for content-addressed assets. Honor correct status codes, ETags and cache policy for encoded responses. Serve HEAD without a body. Verify whether the loader needs ranges. If so, implement and test correct encoded-representation `206`/range behavior on the chosen backend, with cache and encoding headers. Do not treat a cached error page as an asset. Retain the last good asset generation during rollback and for players who already loaded its HTML. For Static Assets, stage the retained manifest and its bytes alongside the new generation so they resolve on the currently deployed version. Keep the route tests for a retained release ID and a nonexistent ID.
4. Workers Static Assets has a 25 MiB individual-file limit, and this repo uses a strict less-than cap. Enforce `size < 25 * 1024 * 1024` on every file staged for static upload, including legacy files. Check the total file count against the current plan. If a Web file exceeds the cap, measure which assets drive the payload. Consider excluding debug/unused content and splitting optional large station/content bundles into lazy Unity loads first. For example, Tianhe's source document is about 16.8 MB before Unity packing. If an artifact remains too large, use private R2 for the entire Unity immutable generation and keep HTML, TS and small mutable metadata in Static Assets. [Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
5. R2 branch, only after owner approval. Add a staging and production binding using distinct buckets. Upload each exact versioned object via Wrangler or a scripted S3-compatible upload, recording SHA-256, size and HTTP metadata. Read back the manifest/object headers and verify staged bytes. Stream `R2ObjectBody.body` through the Worker with MIME/encoding and stable cache keys. Cache successful immutable GETs as measured, preserve ETags, serve HEAD via object metadata, and keep keys private behind the validated prefix. Deploy only after every object is verified. Retain at least the active and previous known-good generations and any needed by in-flight HTML. [R2 Worker binding](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)

## W4. Automate local and staging verification

```powershell
# Planned wrapper and local config after B4 and W1.
./unity/scripts/metro-unity.ps1 build-web -Configuration Release
./unity/scripts/metro-unity.ps1 pack-web
npx wrangler dev --config .preview/unity/wrangler.local.jsonc --port 8787
# Run in a second shell or have smoke-web manage the process lifecycle.
./unity/scripts/metro-unity.ps1 smoke-web -BaseUrl http://127.0.0.1:8787
```

1. Smoke HTTP from both languages, demo deep links, benchmark/lab, missing files, asset handling under workers.dev root, `HEAD`, query-preserving redirects, and non-game routes through an integrated staging setup. Run `curl.exe -I` and GETs using an explicit `Accept-Encoding` on HTTPS. Verify raw encoded payload digests with the encoding negotiated and no client decompression. Verify decoded WASM magic and artifact hash separately. Check that the path and header match the loader's observed requests.
2. Use the repo browser harness for Chromium and add Playwright only if it simplifies the selected browser matrix. The real browser test waits for a Unity ready marker after a rendered frame, exercises pointer input, reads locale and station ID, checks console/network failures and verifies save continuity across reloads. Test a missing WASM request and broken capability/initialization state with a localized shell error. Playwright WebKit smoke complements real Safari where it is part of the supported matrix. [Playwright browsers](https://playwright.dev/docs/browsers)
3. Deploy first to a separate staging Worker name without any production routes. Use an explicit staging config and test both mount styles where applicable. Allowlist demo/QA fixtures and turn off telemetry in staging. Record exact version and URL. Run the route/browser checks on the actual HTTPS staging endpoint, with compressed files and cold/warm loads. Rehearse the engine switch and rollback there.

## W5. Hand off from the current Cloudflare build trigger

1. Use a licensed build workstation initially. Run Unity tests/build/pack, then send a single checksummed artifact to the deploy step. Later, move the same commands to a licensed Windows or compatible Linux runner and use trusted CI jobs with pinned editor/module and package locks. A Cloudflare Workers Builds job consumes a verified artifact or builds the TS/static components with Node. It does not need to acquire a Unity license or invoke Unity.
2. Before publishing Unity, inspect active `metro-game` versions and its linked Workers Builds trigger. The documented `main` trigger runs `npm run build:game` followed by `npx wrangler deploy -c game/wrangler.jsonc`. Disable or replace that deploy producer before switching. Otherwise a later commit can silently republish the TS game or deploy an incompatible asset directory. Record the old trigger settings and restoration steps. Use the Cloudflare Builds trigger API where permissions allow. If account-side controls require a dashboard change, have the owner handle that one-time setup. Confirm no in-flight deploy remains. Preserve the separate `metro` site build trigger. [Workers Builds Git integration](https://developers.cloudflare.com/workers/ci-cd/builds/git-integration/) · [Build trigger API](https://developers.cloudflare.com/api/resources/workers_builds/subresources/triggers/methods/update/)
3. For the first release, let the licensed runner or a separate authorized deploy job own `metro-game`. Give only the deploy step the scoped Cloudflare credential and account ID. Require an artifact checksum, exact Worker, config and environment, expected current Worker version, and engine mode as inputs. Refuse publishing from a dirty tree or with missing QA gates. Serialize deploys, verify the old expected version immediately before publishing, and record the new active version plus the release manifest.

## W6. Switch the existing production Worker

1. Confirm owner decisions, the asset provenance gate, all parity and performance gates, artifact signature or checksum, and a known-good previous deployment. Save the previous Worker version, deployment config and TS build inputs. Confirm R2 binding and object retention if used.
2. Dry-run with the intended release config, inspect routes/bindings and list files. Deploy using `npx wrangler deploy --config game/wrangler.jsonc` after that config points to the packed release, or promote a previously validated version through Wrangler versions/deployments. Keep the route pair and Worker identity stable. Use a release ID visible in diagnostics and response headers.
3. Immediately rerun the HTTP route matrix and browser smokes against the apex. Validate the site links from `/en/`, demo canonicalization, actual loaded Unity release ID, existing local v1 save migration with a synthetic seeded browser profile, user file export/import, and legacy access. Check that stats traffic remains within the approved scope.

## W7. Rollback and finish

1. If the Unity player fails to boot, route/language behavior regresses, saves fail or gates deteriorate, switch to a tested legacy-mode release or use `npx wrangler rollback <known-good-version-id> --config game/wrangler.jsonc`. Verify the active version and the same public route matrix. Preserve bindings and artifact objects required by that version. If rollback cannot restore a deleted binding or release, redeploy the recorded legacy commit/config/artifact. [Cloudflare rollback constraints](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)
2. Validate player data after rollback. The old TS key remains available. Unity progress uses its separate storage and can be exported as a v1 save and opened by TS. Keep a documented path to the Unity preview/export utility if the public Unity entry is withdrawn. If that recovery requires the original browser origin, keep a same-origin recovery URL or make the reviewed recovery script read the Unity key locally. Test this with a seeded profile before the public switch.
3. Hand off source and artifact checksums, Unity/TS build scripts, deployment logs, version IDs, route matrix, QA results and recovery steps. Retire the legacy path and old generations only after the owner agrees on a retention period and downstream art/video, benchmark and stats workflows have an explicit home.
