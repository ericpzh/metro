# Tianhe Park Three.js implementation review fixes

Fix the issues found in the browser performance port and verify gameplay and rendering before the final benchmark. The parent plan defines the original optimization scope and performance targets. [Three.js performance plan](threejs-tianhe-performance-plan.md)

## Implementation review fixes

Land these fixes before the final benchmark. Each item needs a regression that fails on the reviewed implementation and passes with the fix.

1. **Pair density with the graph that produced it.** Publish fresh graph coordinates after a topology rebuild, with a station generation and graph revision shared by the graph and density messages. Install the graph before its first density sample. Clear stale overlays on station switch or graph replacement, and consume density only when both identifiers match, including during renderer recreation. Test a paused edit, undo/redo, and a station switch. Include an edit that changes the node count and one that moves nodes while preserving the count. Verify both cases draw at the new coordinates. [Worker](../game/src/sim/worker.ts) · [Viewport](../game/src/app/Viewport.tsx) · [Worker tests](../game/test/worker-preview.test.mjs)

2. **Refresh density without interrupting motion.** While paused, answer a density request with a density-only sample for the installed graph. During playback, attach density to the next scheduled state frame. Route density-only samples directly to the overlay so they leave the current pose pair, interpolation origin, metrics, history, and route preview intact. Test enabling, disabling, and re-enabling density midway through an interpolation at 1×, and enabling it while paused. Assert that playback delivers no extra motion sample or tick and that a paused density refresh arrives without advancing the world. [Protocol](../game/src/sim/protocol.ts) · [Store consumer](../game/src/app/store/slices/SimSlice.ts)

3. **Initialize replacement clocks at the current time.** Invalidate the clock fast path when any placed or preview rig changes, using registration invalidation or per-rig applied state. Test replacing a non-first placed clock while paused with the same rig count and replacing a hover preview at the same simulated time. The replacement must show the current time and calendar on its first frame. An unchanged rig must still skip redundant writes. [Clock system](../game/src/render/scene/systems/ClockSystem.ts) · [Clock tests](../game/test/clock.test.mjs)

4. **Refresh escalators when their parts become drawable.** Keep the accumulated phase when a hidden escalator or omitted detail part skips matrix writes. After visibility and detail are resolved, apply the current phase to newly drawable parts before submitting the frame, including while paused. Test hiding an escalator during playback, pausing, and revealing it. Also switch from Low to High while paused and verify that the reappearing nosings and risers match the treads at the same phase. Verify the first resumed frame advances from that phase. [Lift system](../game/src/render/scene/systems/LiftSystem.ts) · [Escalator model](../game/src/render/models/pieces/EscalatorModel.ts)

5. **Use the surviving equipment material after a retained edit.** Resolve a bucket's material from its live sources when rebuilding the entry. A single surviving owner uses its own material or live atlas material. A bucket with several equivalent material owners uses a batch-owned canonical material. Test two matching equipment models with Low proxies, delete the first owner, and assert that the surviving draw uses the live owner's material. Verify undo/redo, section clipping, and disposal through both native and fallback batching. [Equipment batches](../game/src/render/equipmentBatches.ts) · [Batch lifecycle tests](../game/test/batching-lifecycle.test.mjs)

6. **Apply the floor's current wall setting on deferred publication.** Initialize each incoming wall mesh from the owning tray's current wall visibility before attaching it. Test hiding walls after the first structure frame and before flushing the remaining equipment. The new wall meshes must stay hidden and excluded from picks, and showing walls again must restore them without changing tray placement. [Exploded layout](../game/src/render/explodedLayout.ts) · [Exploded tests](../game/test/exploded-view.test.mjs)

7. **Preserve transparent draw ordering in Exploded view.** Limit new cross-source material canonicalization and atlas merging to opaque surfaces. Preserve the prior draw boundaries for transparent surfaces that relied on independent depth sorting. Check both separately owned untextured materials and textured faces eligible for the atlas. In a browser, orbit overlapping translucent surfaces with a third tinted surface between them and verify the blend order from both sides. [Exploded layout](../game/src/render/explodedLayout.ts) · [Material keys](../game/src/render/materialCanonical.ts) · [Browser check](../tools/check-exploded-view.mjs)

8. **Bound the TV visibility lookup.** Use the module root index, or maintain an index keyed by module id at registration and removal. Check current ancestor visibility for each indexed root so reveal, hide, move, and undo/redo use live state. Keep the one-panel repaint budget and the existing atlas upload budget. Use a deterministic work-count test with hidden pending TVs and unrelated module roots to verify that increasing station size adds no root scans to repaint selection. Verify a revealed TV is prioritized and shows the latest queued content. [Module system](../game/src/render/scene/systems/ModuleSystem.ts) · [TV repaint queue](../game/src/render/scene/systems/PlateSystem.ts) · [Tianhe regression tests](../game/test/threejs-tianhe-perf.test.mjs)

- Run three matched captures for each Tianhe view and quality at 16× using the production runner. Follow the parent plan for smaller-station and presentation coverage. [Acceptance criteria](threejs-tianhe-performance-plan.md#verification-and-acceptance) · [Benchmark runner](../tools/bench-sim-stalls.mjs)
- Record submitted-frame and rAF timings separately. Compare average FPS, 1% low, p95/p99, worst frame, draw calls, and peak JS and process memory. Report the full 30-second window and a steady-state window chosen before the comparison. Capture the times to structure ready and equipment ready separately. Visible workload must match at fixed ticks and camera positions. Instrument completed worker ticks at the source, delivered tick IDs at the consumer, and the tick ID used for each submitted frame. Expect about **480 ticks in 30 s** at 16×, scaled to the actual window, with at most one tick of sampling uncertainty per endpoint. Report timer misses and publication lag. A run with less simulation work can diagnose a bottleneck and cannot establish an FPS gain.
